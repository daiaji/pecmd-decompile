# 逆向验证方法论 · R27 轮次复盘（Lua 对齐前置参考）

> 成文于 R27-d（2026-09-03），承用户要求："开始 Lua 对齐前，把教训和经验都更新到文档"。
> 素材 = R26-i ~ R27-d 全程（PART 收口 → 语料扩展 → VHD 验证 → 3+2 个真 bug 修复）。
> 受众：下一位逆向/移植代理 + Lua 对齐实施者。每条教训附「对 Lua 对齐的含义」。

---

## 0. 一句话总纲

**语料（行为对拍）是裁决者，汇编是复核者，Ghidra(dc) 是参考者，msvc C 是参考实现——永远不要拿后者的推断压过前两者的实证。**

本轮 5 个真实缺陷（i28g 双游标合并 / 词扫描吞逗号 / PhysicalDrive 转义丢失 /
ParseHexOrDec 零参桩 / 012 桩惯例回归）**没有一个**是先读代码读出来的——全部是
"语料或实测先暴露分歧 → 追到根因"。反过来，凡是我"推理觉得很对"的（如 dc:90913
清零语义、hdN 词边界），几乎都错了一半。这就是本文件想让你少走的路。

## 1. 验证先行：对拍语料是最高证据

### 1.1 语料一上就抓 bug（本轮实例）
| 语料/探针 | 抓出的缺陷 | 性质 |
|---|---|---|
| FORX 068（NL:/delims: 变体矩阵） | i28b delims: 分支误置 `uVar33=6` | dc 不对称性被"翻译对称化" |
| PART 069/探针（list disk） | i28g 双游标合并 → 子命令匹配空串 | Ghidra 寄存器变量被合并 |
| PART 069 重测 | 词扫描缺 ',' 终止（汇编 cmp ax,di） | Ghidra 条件翻译错误 |
| PART 探针（hdN 路径） | ParseHexOrDec 零参桩（恒 1 不解析） | 桩"返回成功"静默吞错 |
| 全量回归（012） | 桩惯例被破坏 → 时序敏感崩溃 | 改桩没查消费方惯例 |

### 1.2 经验
- **先建语料，再修代码**。反向顺序（先修再验）会把"修错了但没测出来"留到下次。
- 语料要覆盖**失败形态**（exit 码、零输出、部分输出）——原版的行为即规格，
  包括它的"怪"（如 FORX NL 零迭代 + exit=2 是原版语义的一部分）。
- 判据必须是**值级**（diff_case vars_val）而非存在级（vars 只证明变量被建了）。
  存在级曾把值完全不同的两端判成 PASS——假绿比红更危险（它会让你停止排查）。

### 1.3 对 Lua 对齐的含义
- Lua 的每个命令实现，验收 = 同一语料 vs 原版 golden（值级），不是 vs msvc C。
- msvc C 是"参考实现"不是"基准"——两端对不上时先问谁对，答案在原版实测。
- 语料缺失的动词（reverse-map 证据列 = 语料验证 之外的行）默认"未验证"，
  Lua 对齐到它之前应就地补语料（补证发生在有真实消费时，见 §6）。

## 2. Ghidra(dc) 可信度分级（移植/Lua 读 dc 前必读）

dc 反编译是**好地图但不是好地形图**——三处系统性失真：

### 2.1 块行序不可靠（本轮最重要教训）
实例：dc:90913 `local_434 = 0xfffc0000`（清零）文本上排在 hd 数字解析
（dc:90873）**之后**，读起来像"解析后被清零"；windbg 实测执行序是**清零在前、解析在后**
（0x14008ecab 命中与否证伪），且清零块实际属于 **-img 分支**（hd 路径根本不经过）。
推论：**同函数的 dc 行序 ≠ 执行序**（Ghidra 按块重排输出），带 goto 的大函数尤甚。

### 2.2 单语句 if 的花括号假象
dc 大量 `if (cond) goto X;` **没有花括号**——被翻译成 C 时"顺手加 {}"会凭空多一层，
整个后续缩进/闭合链全错位（i28g 共 7 处此类）。**翻译前先数清楚 if 体的边界**
（看 dc 下一行缩进/下一个分号，别信视觉上的"块"）。

### 2.3 条件/常量翻译错误
实例：词扫描终止条件，汇编是 `cmp ax,di`（di=逗号定界符），Ghidra 反编译成
`!= L'\0'`——两者行为差一个逗号，hdN 全线失败。**凡是边界/循环条件，回汇编核**。

### 2.4 变参/调用参数丢失
实例：12-spec 格式串只恢复 2 个变参（源码还留着 `TODO(verify)` 没做完）——
wvsprintfW 读栈垃圾 → AV。**Ghidra 丢参是常态不是意外**：见到宽格式串/多参调用，
以 capstone 看 rcx/rdx/r8/r9 + 栈参数准备指令为准。

### 2.5 转义/字面量在落码时二次丢失
实例：`L"\\\\.\\PhysicalDrive%d"`（源文本两个反斜杠对）落成
`L"\.\PhysicalDrive%d"`（一个）——设备路径变 `\.\PhysicalDrive` 直接打不开。
宽字符串字面量是"翻译降级"高发区，对照 dc 时按字符数核对。

### 2.6 对 Lua 对齐的含义
- **Lua 不要照抄 msvc C 的"翻译痕迹"**（双游标、SBORROW、整形强转）——那是 C 对
  Ghidra 的妥协；Lua 要的是**行为语义**，读 dc + 汇编定语义，读语料验语义。
- dc 有疑问处（边界/丢参/行序矛盾）：查 capstone；再矛盾：windbg 活体（§3）。
- dc 的"伪影注释"（`— 寄存器残影, 不落码`）已被证多次正确，可放心跳过；
  但"看起来有语义"的行（清零点、赋值点）必须怀疑是不是别的分支的残影。

## 3. 汇编(capstone)与活体(windbg)是裁决手段

### 3.1 分层裁决链
```
语料实测（行为）  ──矛盾──►  dc 反编译
     │                              │
     ▼                              ▼
  判定基准                    capstone 汇编复核
     │                              │
     └────────── 仍矛盾 ──► windbg 活体（断点看执行序/寄存器/栈）
```
本轮每次"dc 与实测矛盾"最后都由汇编或活体一锤定音，无一例外。

### 3.2 活体的正确姿势（踩坑后）
- **断点只下在"执行序分叉点"**（哪个先跑、哪条分支），不是函数入口——
  本轮 0x14008ecab/ed35/e663 三断点直接定案清零分支归属。
- `sxe -c "kn 5" av` 让 AV 自动停下并打栈——比人肉猜崩溃点快一个数量级。
- 崩在**自己插的桩**里（WritePrivateProfileStringW 传了 int 当指针）也是情报：
  说明崩溃不在主路径，先修桩再定位。
- 调试会话会**持有目标进程** → 释放前无法覆盖 exe（`cp: Device or resource busy`），
  结束会话用 end_session 逐个收。

### 3.3 对 Lua 对齐的含义
Lua 实施者基本不需要这两层（语料就是你的裁决）；仅在"语料两边都怪但一致"
需要解释时才回 dc——记住 dc 可能错，原版实测不会。

## 4. 桩的反模式（移植缺陷的最大来源）

### 4.1 三种桩毒
| 毒 | 症状 | 实例 |
|---|---|---|
| 零参桩"返回成功" | 调用方以为解析成功，值不动 → 远处表现为参数错误/零输出 | `int PECMD_ParseHexOrDec() { return 1; }` → hdN E_INVALIDARG |
| 桩遮蔽真体 | 同名真体存在但链接选了桩（D-01 型） | restored_bodies 封装调桩 |
| 桩惯例依赖 | 别处消费方依赖桩"不改参"的怪语义 | 改桩后 012 时序崩溃 |

### 4.2 排查口诀
- 症状是"参数错/零输出/莫名失败"→ **先看链接映射**（`grep ParseHexOrDec
  build/msvc/pecmd_msvc.map`）确认调用链上每个符号落哪个 obj——桩在 map 里形如
  `unimplemented_stubs.obj`。
- 修桩前读 stubs_common.h 同文件注释（`按 XX 桩惯例` 字样 = 有消费方依赖怪语义）。
- 有真体（core_exec5.c 的 FUN_1400C1194）→ 让**封装改道真体**，桩原样保留，
  比"把桩改成转发"安全（后者动全局符号，前者只动一条链）。
  （最终修复 = restored_bodies 封装内联 extern + 调 FUN_1400C1194，桩原样。）

### 4.3 对 Lua 对齐的含义
reverse-map F 段（接口缺口）清零 ≠ 行为可信：F 段外的"真体"行也可能经桩间接
退化（本轮 ParseHexOrDec 就在"真体封装"下藏了个桩）。Lua 对齐只信
**语料验证列**；真体直移列 = "实现可信，行为待语料"。

## 5. 安全测试方法论：VHD 虚拟盘（PART 类磁盘操作唯一出路）

### 5.1 结论
PART（分区写/读）验证 = **diskpart 建固定 VHD → attach → Get-Disk 按 VHD 路径
定位磁盘号 → PART 只操作该号 → detach+删盘**。全程不存在触碰实体盘的路径。
已沉淀为 run_case.py 的 `manifest {"vhd": true}` 夹具（含 @VHDDISK@ 模板注入）。

### 5.2 工程细节（都是踩过的）
- **磁盘号必须按 VHD 文件路径定位**（`Where-Object Location -like "*part_case.vhdx*"`），
  绝不猜号——猜号在插了 U 盘的机器上就是事故。
- **attach 返回 ≠ 盘就绪**：diskpart 退出后 OS 枚举可能还没完成，list 会少盘。
  轮询 Get-Disk 直到号出现 + 再稳一拍（069 flaky 根因）。
- **每后端独立 VHD**（orig 与 msvc 各建各的），避免共享盘号冲突。
- **测试后清理**：残留挂载的 VHD 会污染下一次 golden 录制（069 golden 曾
  录到带调试盘的列表）。teardown 里 detach + 删文件，失败也要删。
- 探针脚本与语料分离：探针（tools/_r27*.py）试语法/找分歧；语料
  （harness/corpus）锁已定案的形态。

### 5.3 对 Lua 对齐的含义
- Lua 实现 PART 写族（init/clean/-gpt/-mbr）时，验证环境 = 同一个 VHD 夹具。
- 优先实现"list 族"（只读、值级可判）；写族需要 hdN 指定形态（见遗留 §7）。

## 6. 方言定案：实测优先于文档与直觉

本轮实测钉死的方言（原版行为，Lua 直接照此实现）：
- **FORX /L**：`FORX /L 起始 步长 终值,变量,命令`——三数字是同一逗号段内
  **空格分隔**的三元组（直觉"逗号分隔"是错的，会 0x80070057）；负步长反向。
- **FORX NL:/delims: 不对称**：`/NL:` 走变量查找（ENVI 全局变量不可作源，
  表隔离）；`/delims:` 源=第一段字面（不查变量）。两者 opts 不同是原版语义，
  不是 bug。
- **PART 字段模型**：`PART list disk,变量` 变量名在第二逗号字段；
  `PART list disk hdN,变量` 指定盘。
- **WRIT**：39 变体实测基础形式全安全；修饰符 `*v` 是写变量（无文件副作用）。

### 对 Lua 对齐的含义
文档（chunks/re-notes）与实测冲突时**信实测**——chunks 的 FORX 注记当时还说
"msvc 是缩水桩"（那是 R26-e 前的旧状态）。re-notes 的"待实测"清单就是
Lua 对齐的探路地图。
