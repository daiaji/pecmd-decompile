## 1. 身份判定与签名修正

### 1.1 动词归属（置信度：高，四重证据）

两个 25 字节包装器是动词分派表中的尾调包装，调用方在 dc 大解释器 `FUN_14004c0bc`（dc:43816，size=8717）内：

| fourcc | 动词 | 包装器 | param_3 | dc 证据 |
|---|---|---|---|---|
| `0x58454649` = `"IFEX"` | IFEX | `FUN_140035b08` | **1** | dc:45105–45115 |
| `0x444e4946` = `"FIND"` | FIND | `FUN_140035b24` | **0** | dc:44403–44414 |

两处调用点还有一致的预处理（dc:44409 / 45111）：

```c
plVar10 = local_res20;                       // out 变量指针（param_4）
if (*(short *)(LVar25.QuadPart + 8U) == 0x7c) // 参数文本首字符 == '|'
    plVar10 = NULL;                          // 则不传 out 变量
```

即：**行首 `|` ⇒ 禁用结果变量绑定**——与函数体内 `[RSP+0x47]`（'|' 出现标志）驱动的另一条执行路径互相呼应（见 §4.6）。

重构库既有命名与此完全一致：`PECMD_IfexCmdHandler@0x140035b08`、`PECMD_FindCmdHandler@0x140035b24`（core_b2a.c:136/147）、`PECMD_EvalLoopCondition@0x140032dc4`（core_b2f.c:2655）。

### 1.2 签名修正（置信度：高）

dc 存根签名 `HMENU __fastcall FUN_140034788(longlong*, ULARGE_INTEGER, byte, longlong*, undefined8)` 两处错误：

1. **HMENU 是误推返回类型**——真实返回为 8 字节整数状态/结果（§5.d）。
2. **param_2 不是 ULARGE_INTEGER 数值**——home 槽 `[RSP+0x138]` 全程被当作 **LPCWSTR 光标**读写（如 0x1400349E1 `MOV RDX,[RSP+0x138]` 后按 `word [RDX]` 取字符），实参是指向命令文本的宽字符串指针。

还原签名：

```c
int64_t FUN_140034788(ScriptCtx *script,      /* RCX, home [rsp+0x130] */
                      LPCWSTR    cmdline,     /* RDX, home [rsp+0x138] */
                      uint8_t    verb_mode,   /* R8B, home [rsp+0x140] : 1=IFEX, 0=FIND */
                      int64_t   *out_var,     /* R9,  home [rsp+0x148] */
                      void      *locale);     /* [rsp+0x28], home [rsp+0x150]，pthreadmbcinfo */
```

栈帧推导：入口 `MOV [rsp_t+0x8..0x20], rcx/rdx/r8b/r9`（0x14003478B–0x140034797）→ 8×PUSH（RBX,RBP,RSI,RDI,R12,R13,R14,R15 = 64B）→ `SUB RSP,0xE8`（0x1400347A7）。故 home 槽换算：`[T+n] ≡ [RSP_final + n + 0x128]`，即 `[rsp+0x130]=param_1`、`[rsp+0x138]=param_2`、**`[rsp+0x140]=param_3`**、`[rsp+0x148]=param_4`、`[rsp+0x150]=param_5`。

### 3.7 间接调用槽位破译表（二级 API 跳转表）

## 4. 五问结论

### (a) param_3=1/0 在体内的真实分支语义 【置信度：机制=高；字符角色细节=中】

**全函数仅一处读取 param_3**：`0x14003473F` 不存在——准确地说唯一消费点是 **`0x14003573F`**：
`MOVZX R8D, byte [RSP+0x140]`，随后 OR 入 bit17/bit16/bit18 组成的标志字，作为第 3 参传入 `FUN_140032dc4`（0x140035760）。它**不**在本函数体内产生任何 if/else 分叉——真正的分叉发生在 callee 内部的语法档位选择上。

在 `FUN_140032dc4`（dc:30355 起）中，第 3 参低 8 位选择**条件/动作分隔符字符集**（反编译实证）：

```
uVar3  = p3 & 0xff;
mode0(FIND):  local_1a4='|'(0x7C), local_168='$'(0x24), local_180='#'(0x23), lead='$'
mode1(IFEX):  local_168='|'(0x7C), local_1a4='$'(0x24), local_180='#'(0x23), lead='|'
mode2(ExecPathList 族): 全部哨兵值 0x10000x（禁用），local_158='|'
```

即：**IFEX 以 `|` 为第一分隔符、`$` 为第二分隔符；FIND 将两者对调（`$` 第一、`|` 第二）；`#` 两者共用**。这组字符决定 032dc4 内 operand/action 分类、尾随动作是否存在等语法判定（LAB_140033300/LAB_140033FB7 一带的多重 `!= local_168/local_1a4/local_180` 比较）。

高三位修饰（与 verb_mode 同路传递，非 IFEX/FIND 差异）：
- bit16 `*c` → 032dc4 内 `local_c8` 非零 ⇒ 字符串比较用 `StrCmpNW`（区分大小写），否则 `StrCmpNIW`；
- bit17 `*ab` → `local_c0`，参与空串操作数/绝对路径判定组合（精确语义存疑，见 Q4）；
- bit18 `*var` → `local_128`，影响左操作数走变量查询路径（`FUN_14001e69c`/`FUN_14006f884`）而非命令执行。

旁证：调用方对 `|` 的处理（dc:44409/45111 首字符 `|` ⇒ out=NULL）与体内 `[RSP+0x47]!=0` 时改走 `FUN_140025474` 二选一执行路径相容——`|` 在 FIND 语法里兼有“第二分隔符”身份。

### (d) 返回值类型与语义 【置信度：类型=高；取值全集=中】

类型为 **8 字节整数**（RAX），dc 的 HMENU 属误推。观测到的返回来源：

1. `0` —— cmdline 修剪后为空（0x14003495C）或表达式路径无可执行部分（RDI 保持 0）；
2. `FUN_14004c0bc(...)` 的返回（0x1400357EA→RDI）——递归解释器执行真分支动作的结果；
3. `FUN_1400a53e4(...)` 的返回（0x1400357BE→RDI）——脚本动作执行器的状态；
4. `FUN_140025474(...)` 的返回（0x140035839→RDI）——管道模式执行所选分支的状态；
5. `MOVSXD RAX,ESI`（0x1400350F6）/ `MOV RSI,RAX`（0x1400353C8）——错误码与小整数结果：
   - `0x80070057`（E_INVALIDARG）：选项参数缺失/非法（0x140034A4F 起，多处写入）；
   - `0xD`(13)、`0x23`(35)：个别 `--pid/--wid` 解析失败路径把内部小常数误作状态写入 ESI（0x140034EB4 `MOV ESI,R12D`，此处 R12D 可能是 0x80070057 也可能是残留 0x23——低置信，见 Q5）；
   - `GetMenuItemCount` 的返回值（`--menu` 无 `#id` 且计数>0 路径，0x14003520A `MOVSXD RSI,EAX`）。

综合判断：语义上是 **“状态码｜被执行动作的结果值”混合通道**，正值的布尔化用法由调用方完成（032dc4 结果即以 `>0` SETG 判定）。建议重构库以 `int64_t` 建模，命名建议 `PECMD_IfexFindExecutor`。

## 7. 遗留疑问清单

1. **Q1** `--pid` 路径 `FUN_14002d708` 第 2 参的组合编码（`R14B|EBX|[rsp+0x68]`）中 `--user` 的 0x80000 与 `*c` bit16 同槽叠加，具体位义需读 27142 函数体后段才能拆清。
2. **Q2** `--menu` 无 `#id` 路径调用 `GetMenu(hwnd)` 后返回值被弃用——是纯校验还是存在被 Ghidra 吞掉的副作用？
3. **Q3** `|` 模式下条件为真传给 `FUN_140025474` 的是 `[rsp+0x50]`（通常为“条件”侧文本）——是否意味着该语法实际是 `<cmd>|<alt>`（管道备选）而非 `<cond>|<action>`？需用样例脚本动态验证。
